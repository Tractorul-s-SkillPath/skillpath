# SkillPath

Assess a skill, find the gaps, work the plan.

A student picks a skill category, takes a multiple-choice assessment, gets a
score with their weak areas identified, and receives a learning plan built from
those weak areas. An admin manages the category catalog and question bank and
sees aggregate data.

Next.js (App Router) · TypeScript · Supabase (Postgres) · Tailwind.

---

## Running it

**1. Install**

```bash
npm install
```

**2. Create a Supabase project** and copy the environment template

```bash
cp .env.example .env.local
```

Fill in `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` from
Project Settings → API Keys, then generate a session secret:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

**3. Apply the schema**

The migrations are in `supabase/migrations/`, applied in filename order — the
schema first, then RLS, then the later changes. Apply them with the Supabase
CLI (`supabase db push`), or paste them into the SQL editor in that same order
if you are working against a hosted project you did not create locally.

[`lib/supabase/database.types.ts`](lib/supabase/database.types.ts) is
hand-written rather than generated by `supabase gen types`, so it can drift from
the migrations. When the two disagree, the migrations are the schema and the
types file is the bug.

**4. Seed demo content**

```bash
npm run seed
```

Creates the demo accounts, the baseline category and four real ones, their
question banks, and assessment history for the three students. It is idempotent
— every step matches on a natural key and inserts only what is missing, so
re-running it never duplicates a bank. `npm run seed:users` does the accounts
alone; `npm run seed:e2e` does the same against the project named in `.env.e2e`.

You can also build a catalog by hand instead: register at `/register` and use
the admin console at `/admin/categories`.

**5. Start**

```bash
npm run dev
```

Sign in at `/login` with one of the seeded accounts, or register your own. To
reach the admin side, register a new account, pick _Administrator_ and tick the
manager-approval box, or flip `role` to `'admin'` on an existing row in the
Supabase table editor.

## Read this before pointing it at anything real

The two deferrals this section used to warn about have both been closed:
sign-in goes through Supabase Auth and verifies the password
(`app/(auth)/login/actions.ts`), and Row Level Security is enabled on all ten
tables with policies (`supabase/migrations/20260902204628_securitate_rls.sql`).
The `users` table no longer has a `password` column of its own.

**One thing RLS did not close, and it is the one that matters: the answer key is
still obtainable.** `answers` has a single read policy, `for select using
(true)`, on top of a blanket `grant all on all tables … to anon` in the schema
migration. RLS filters _rows_, never _columns_, so any holder of the publishable
key can `GET /rest/v1/answers?select=is_correct` and read the lot. The
application layer is careful — `question.service` never selects the column and
`response.repo.listForRun` names its columns — and one direct request defeats
all of it. SP-004's second acceptance criterion is not satisfied, and the
`answer_options` view meant to fix it (§5) does not exist in any migration.

## Layout

```
app/            routes. (auth) · (student) · (admin) route groups
components/     shared presentational components; ui/ is the design system
lib/
  domain/       pure functions — scoring, levels, badges, quests. No I/O
  services/     orchestration; the only thing pages call
  repositories/ the only files importing supabase-js
  validation/   Zod schemas, shared client and server
  auth/         session cookie, assertAuth, assertAdmin
  supabase/     the client, and database.types.ts — hand-written, can drift
docs/           ARCHITECTURE.md · BACKLOG.md · TESTING.md
supabase/       migrations/ — the schema of record — plus config.toml, seed.sql
scripts/        seed.mjs, seed-users.mjs
tests/          Vitest: 43 files, 481 tests. tests/db/ needs a live project
e2e/            Playwright specs and their global setup
```

Dependencies point downward only: a page never touches a repository, a
repository never calls a service. [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md)
§3 is the rule and it is short.

## What is built

**Working end to end:** the landing page, register / sign in / sign out, the
student profile (identity, interests with a level each, assessment history,
learning plan with a status control, XP, badges, quests, leaderboard), the
student dashboard, and the whole admin console — overview tiles, the
weak-categories chart, users, the category catalog, the question bank inside
each category, and the results table, with URL-state filters and server-side
paging throughout.

**Also working: taking an assessment**, which this section described as unbuilt
for a long time. `/assessments`, `/assessments/baseline`, `/assessments/[id]`,
its results page and `/plan` are all real, grading runs server-side through the
`grade_assessment()` RPC, and the E2E baseline journey walks register → baseline
→ results → plan against a live database on every run.

**Not built:** the three AI features — `lib/ai/` is six comment-only files, 92
lines, no implementations. Four other source files are still comment-only
sketches: `lib/domain/{scoring,weak-areas,feedback}.ts` and
`lib/repositories/progress.repo.ts`, which is why there is no score-trend chart.
Their tests are written and waiting, excluded by name in `vitest.config.ts`.

[`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) §0 has the full built/not-built
breakdown, and [`docs/BACKLOG.md`](docs/BACKLOG.md) has the stories with their
current status.

## Scripts

| Command                               | Does                                                                      |
| ------------------------------------- | ------------------------------------------------------------------------- |
| `npm run dev`                         | Development server                                                        |
| `npm run build`                       | Production build                                                          |
| `npm run start`                       | Serve the production build                                                |
| `npm run typecheck`                   | `tsc --noEmit`                                                            |
| `npm run format`                      | Prettier, writing in place. `format:check` is the same thing read-only    |
| `npm run lint`                        | ESLint, flat config. `lint:fix` applies the fixable ones                  |
| `npm run test`                        | Vitest, watch mode. `test:run` for one pass, `test:coverage` for the gate |
| `npm run test:db`                     | The tests that need a live Supabase project — see `vitest.config.db.ts`   |
| `npm run test:e2e`                    | Playwright. `test:e2e:dev` runs it against `next dev` instead of a build  |
| `npm run seed` · `npm run seed:users` | Seed a database. `seed:e2e` seeds the E2E project from `.env.e2e`         |

The four gates worth knowing about are `format:check`, `typecheck`, `lint` and
`test:coverage`. `.github/workflows/ci.yml` runs all four plus `next build` on
every PR and every push to `main`, cheapest first, so a type error does not wait
on a bundle. Running them locally before you push only saves you the round trip;
the workflow is the thing that decides.

Two notes on `lint`, because the output is not self-explanatory. It reports
seven warnings and zero errors, and that is the intended state — see the
`react-hooks/set-state-in-effect` comment in `eslint.config.mjs` for what each
one is and why it is not an error yet. CI fails on errors only, deliberately: no
`--max-warnings`, because pinning a count turns every unrelated change into a
merge conflict with the workflow file.

Branch protection is the one gate the repository cannot switch on for itself. It
has to be enabled in the GitHub settings, and until it is, CI reports but does
not block.
